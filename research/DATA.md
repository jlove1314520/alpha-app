## 1. 還原股價（Split/除權息調整）

### 台股：`TaiwanStockPriceAdj`
```
curl "https://api.finmindtrade.com/api/v4/data?dataset=TaiwanStockPriceAdj&data_id=2330&start_date=2026-08-01"
→ {"msg":"Your level is free. Please update your user level...","status":400}
```
**免費方案完全拿不到還原股價**，不管帶不帶 `data_id` 都一樣被擋（跟期貨三大法人那種「帶對 data_id 就能免費用」的情況不同，這個是真的要收費）。

現在 App／資料管線用的 `TaiwanStockPrice` 是**原始未還原股價**。用實際除息案例驗證邏輯（非數字證據，因為單日漲跌幅度通常遠大於股息金額，光看價格差看不出來）：2330 在 2025-06-12 除息（`TaiwanStockDividend` 查到 `CashExDividendTradingDate:"2025-06-12"`、現金股利 4.5 元），但 FinMind 另外賣一個「還原股價」資料集這件事本身就證明：`TaiwanStockPrice` 不是還原股價，否則沒必要另外賣。

**影響：** 任何用免費 `TaiwanStockPrice` 算報酬率、回測績效的地方，除權息日前後的報酬會被污染（真實報酬被低估，因為除息當天的價格下跌會被誤判成虧損）。台股平均每年除權息一次以上，長期回測**必須**自己還原股價，或想辦法拿到 `TaiwanStockPriceAdj`（付費）或改用 `TaiwanStockDividend`（免費，見下方）自己還原。

**可行的免費替代方案：** `TaiwanStockDividend` 資料集是免費的，含 `CashExDividendTradingDate`、`CashEarningsDistribution`、`StockExDividendTradingDate`（股票股利）等欄位，理論上可以自己寫還原邏輯（在每個除權息日之前的價格，乘上調整係數）。

**✅ 已實作（2026-08-22，`research/adjust.py`）：** 用 TWSE 官方除權息參考價公式，把每次除權息事件換算成一個乘法調整係數，由近到遠往回套用到事件日之前的所有價格：

```
參考價 = (除權息前一交易日收盤 − 現金股利 + 現金增資認購價 × 認股比率) / (1 + 股票股利比率 + 認股比率)
調整係數 = 參考價 / 除權息前一交易日收盤
```

**驗證方式（用 2330 實測，不是理論推導）：**
1. 抓 2330 從 1994 年至今的全部除權息事件（42 筆），檢查係數是否落在合理範圍——2005 年那筆（50% 股票股利＋現金股利，台積電當年高速成長期）係數 0.644，符合「股價因除權大幅回落」的預期；近年（2019 起改季配息）係數都在 0.99 上下，符合「股利相對股價金額小，影響也小」的預期。全部 42 筆係數都落在 (0,1) 區間，沒有出現異常值。
2. **最新一筆資料的 `adj_close` 必須等於 `close`**（今天不能被自己調整）——實測 2026-08-21 那筆 `close=2410.0, adj_close=2410.0`，相等 ✓。
3. **除息日前後的報酬率比對**：2025-06-12 除息（現金股利 4.5 元，除息前一日收盤 1065）。原始報酬率 `close` 從 1065→1045 是 **−1.88%**；調整後 `adj_close` 對應報酬率是 **−1.46%**。兩者差 0.42 個百分點，跟股利機械性影響 `4.5/1065=0.42%` **幾乎完全吻合**——證明調整有確實把除息造成的價格跳空從報酬率裡拿掉，不是隨便亂調。

**已知殘餘缺口（誠實列出，不是隱瞞）：**
- **減資（capital reduction）沒有處理**：`TaiwanStockCapitalReductionReferencePrice` 資料集還沒接進 `adjust.py`。做過減資的股票，在減資日附近這個還原價序列會有一段沒調整到的跳空。目前系統裡還沒遇到需要用到這類股票的案例，先記录，之後真的要用到再補。
- 股票股利/現金增資比率同時發生時的公式，只驗證過 2330 這一檔；還沒有系統性地跑過全市場找出公式在極端案例（例如同時減資又除權）下會不會出錯。

```
curl ".../data?dataset=USStockPrice&data_id=NVDA&start_date=2024-06-05&end_date=2024-06-12"
```
NVDA 在 2024-06-10 盤後執行 10:1 股票分割。抓回來的資料裡，**分割前（6/5–6/7）的 `Close` 就已經是分割後的價格量級（約 $120，而不是分割前實際的約 $1200）**——代表 FinMind 美股資料在分割發生後有回頭把歷史價格改成還原後的數字。`Adj_Close` 另外還做了股利調整（跟 `Close` 有小差距）。

### 美股存活者偏差調查（2026-08-23 馬拉松第四輪）：TW 的兩個候選方法在美股都不可靠

**動機**：`universe.py` 對台股的核心方法是「`TaiwanStockPrice` 有沒有某天的資料列 = 那天是不是能交易的地面真相」，完全不需要額外判斷「上市/下市日」。`US_MARATHON_STATE.md` 原本假設也許可以照搬同樣精神，或退而求其次用 `USStockInfo` 289 個快照的成員增減來反推。**這輪用 5 檔已知下市/出事的美股實測這兩個假設，結果都不成立，是重要的負面發現。**

**測試腳本**：`research/us_survivorship_probe.py`（全部走 `load_dev()`／`_fetch()`，未動 holdout）。挑了 5 檔涵蓋不同下市原因、不同年份的股票：`TWTR`（被馬斯克收購下市，末交易日約 2022-10-27）、`SIVB`（矽谷銀行倒閉被 FDIC 接管，約 2023-03-10）、`SBNY`（Signature Bank 同款，約 2023-03-10）、`FRC`（第一共和銀行倒閉，約 2023-05-01）、`BBBY`（Bed Bath & Beyond 破產下市，約 2023-05-03）。**這些「已知末交易日」是憑一般常識記憶寫進腳本註解的參考值，這輪沒有另外用權威資料源（例如 SEC EDGAR）逐一核實，只拿來做粗略 sanity check，不是地面真相——這點很重要，下面的解讀要考慮這個限制。**

**實測結果 1（`USStockPrice` 是否保留下市股歷史價格）**：
- `TWTR`／`SIVB`／`FRC` 三檔：**完全 EMPTY，一筆資料都沒有**——這是直接從 API 回應讀出的事實，不依賴上面提到的「已知末交易日」是否準確。代表 FinMind 免費層美股價格資料庫**不像台股那樣保留下市股的完整歷史**，這三檔股票對這個資料源來說形同不存在。
- `SBNY`：有 96 筆資料，但全部落在 2024-08-15 至 2024-12-31，**沒有任何一筆早於這個區間**——跟 Signature Bank 2023-03 倒閉的認知完全對不上，代表這個 ticker 現在指向的資料極可能不是原本那家銀行的歷史（可能是代號被重新分配給另一家公司，或這是 FinMind 資料庫本身的錯置，這輪沒有進一步查證是哪一種）。
- `BBBY`：有 5687 筆資料，`first=2002-05-30`、`last=2024-12-31`，橫跨整個「已知下市日」（2023-05-03）前後，**而且用逐日檢查（2023-04 到 2023-09）確認這段期間完全沒有交易缺口、沒有價格異常跳動**——連續得不像「一家公司下市、另一家公司幾個月後接手同一個代號」該有的樣子（真的代號重用通常會有一段停牌空窗或價格量級的劇烈斷層）。**這代表我原本記憶中「Bed Bath & Beyond 在 2023-05 下市」這件事本身可能不準確，或者 FinMind 這個 `BBBY` 資料列從頭到尾都是同一個實體、根本沒有發生我以為的下市事件**——這輪沒有查證到底是哪一種，誠實記錄為未解之謎，不能對這個案例做任何確定性結論。

**實測結果 2（`USStockInfo` 快照增減能否偵測下市）**：
- `TWTR` 是最清楚的反例：儘管實際交易到 2022 年，289 個快照裡**只在 2019-01-10 這一天出現過一次**，其餘全部 288 個快照都沒有它——這代表 `USStockInfo` 快照本身對於「這檔股票現在是否在市場上」的覆蓋率/一致性有嚴重缺口，**跟下市偵測無關，是快照資料本身不完整**，所以拿快照增減來反推上下市窗這個方法從根本上不可靠。
- `SIVB`／`SBNY`：都在倒閉後幾天（2023-03-14／15）才「最後一次」出現在快照裡，時序上矛盾（照理應該在倒閉前的快照裡最後出現，不是倒閉後）。
- `FRC`：最後出現在 2023-03-18，早於「已知下市日」2023-05-01——方向合理，但樣本中唯一一個時序看起來「說得通」的案例。
- `BBBY`：最新快照（2026-08-22）仍然看得到——跟上面「找不到下市證據」的價格資料觀察一致。

**結論（誠實的負面結果，這是這輪最重要的產出）**：
1. **`universe.py` 那套「價格資料列存在 = 地面真相」的方法不能照搬到美股**——至少 3/5 測試案例顯示下市股的價格資料在免費層直接消失，不是保留到最後交易日。
2. **`USStockInfo` 快照增減也不能拿來偵測下市**——`TWTR` 的案例證明快照本身對活躍股票的覆蓋率就不完整，不是只有下市股才會漏掉。
3. **代號重用（ticker reuse）是美股特有、台股沒有的額外陷阱**——`SBNY`／`BBBY` 兩個案例都不排除代號被重新分配給不同公司的可能性，如果之後盲目用「有資料 = 活著」判斷，可能會把兩家不同公司的歷史接成一條連續序列，這比「完全沒資料」更危險（沉默地產生錯誤，不會報錯)。
4. **這輪測試用的「已知下市日」本身未經權威來源核實**，是這次調查方法上的限制，不是最終定論——如果要繼續深挖，下一輪應該先用已經驗證可用的 SEC EDGAR API（`www.sec.gov/files/company_tickers.json` 對照 CIK、`submissions` API 查最後申報記錄）去查證這幾檔股票的真實下市時間，而不是繼續依賴人的記憶。

**下一步（美股存活者偏差，還沒解決，留給後續輪次）**：需要找一個獨立、免費、公開的美股下市股名單資料源（例如交易所公告、或 SEC EDGAR 的 Form 25/25-NSE 下市申報記錄——這個假設下一輪可以驗證），不能依賴 FinMind 的 `USStockPrice`／`USStockInfo` 自行拼湊。

### 美股存活者偏差調查（根本原因）：`FRC`／`SBNY` 查不到 SEC CIK 的真正原因不是查錯，是它們本來就不屬於 SEC EDGAR 管轄（2026-08-24 馬拉松第41輪，`sec_edgar_frc_root_cause_probe.py`）

**動機**：接續第七輪留下的開放問題（正確 FRC CIK 仍未找到）。這輪先把 `browse-edgar` 名稱搜尋的方法窮盡（加測 `type=10-K` 限制的 prefix 搜尋、無 type 限制的 exact-name 搜尋），發現一個新候選 CIK 1097256「FIRST REPUBLIC BANK /MSD」，但查其申報記錄只有 1 筆 2008 年的 `MSDW`（Morgan Stanley Dean Witter）表單——推測是 MSDW 某個結構型商品/信託把 First Republic Bank 當參照實體提及，不是銀行本身的申報人 CIK，排除。至此，`browse-edgar` 名稱搜尋（prefix + exact-name + 有無 `type=10-K` 限制）已經窮盡，沒有任何候選命中一家真正申報過 10-K 的「First Republic Bank」。

**關鍵新發現：把 `efts.sec.gov` 全文檢索從第七輪的窄範圍（`entityName` 過濾）改成完全不限定 entityName、只限定一個正常年份（2019，尚未出事）＋`forms=10-K`，結果 FRC 自己的年報完全不在索引裡**——不限 form 查「First Republic Bank」整年有 7,802 筆命中，但前 20 個 entity bucket 全部是持有 FRC 股票的基金/ETF（Fannie Mae、ProFunds、SPDR 等），不是 FRC 本身；限定只查 10-K 表單，74 筆命中裡也沒有 FRC，全部是不相干的 Sequoia 房貸信託（因為文件裡把 First Republic Bank 列為貸款服務機構而被文字比對命中）跟零星其他銀行。**一家公司自己的年報，在同一年份裡有 7,802 筆「別人提到它」的命中卻完全查不到「它自己申報的文件」，這不是索引缺口，代表這份 10-K 從一開始就沒有進 SEC EDGAR。**

**根本原因（用公開、免登入的 .gov 來源查證，非憑印象）**：《證券交易法》（Securities Exchange Act of 1934）第 12(i) 條規定，**FDIC 承保的「州立、非聯準會會員銀行」（state nonmember banks）如果有依 12(b)/12(g) 條註冊的證券，其定期揭露申報（10-K/10-Q/8-K 等同文件）要直接向 FDIC 申報，依 12 CFR Part 335，不是向 SEC 申報**——因為對這類銀行而言，FDIC（不是 SEC）才是主管證券揭露的機關。（國家銀行向 OCC 申報；州立聯準會會員銀行/銀行控股公司向 Fed 或 SEC 申報。）來源：
  - [FDIC「Bank Securities」頁面](https://www.fdic.gov/accounting/bank-securities)
  - [eCFR 12 CFR Part 335](https://www.ecfr.gov/current/title-12/chapter-III/subchapter-B/part-335)

First Republic Bank 是加州州立特許銀行，且（**這點是本輪依一般公開常識推論、沒有另外逐一查證，標記為假設**）本身沒有另外設立一家獨立的 SEC 掛牌銀行控股公司（跟多數大型 NYSE 上市銀行的慣例——用控股公司當 SEC 申報人、銀行本身不直接申報——不一樣），若同時也不是聯準會會員銀行，就完全符合「FDIC 才是主管機關」的條件。**這一個結構性原因，一次解釋了第4–7輪累積的所有異常**：SEC EDGAR 裡找不到任何「First Republic Bank」名下的 10-K/10-Q/8-K（本輪步驟1–2）、2023年下市查不到 Form 25（第5–7輪，Form 25 是 SEC 表單，本來就不是這類銀行的申報主管機關會用的表單）。**第六輪「FDIC 接管型下市不走標準 Form 25」這個假設應該直接退役、不是繼續降級**——它的前提（假設這些是正常會跟 SEC EDGAR 申報的實體，只是接管後不知為何不交 Form 25）本身就錯了；真正的原因是結構性的、早於 2023 年接管事件就存在，跟有沒有被接管清算無關。`SBNY`（Signature Bank，紐約州立特許銀行）很可能是同款情況，但本輪沒有另外查證 SBNY 是不是聯準會會員銀行，這點仍是假設，留給下一輪。

**確認公開替代資料源存在且可連線**：`https://efr.fdic.gov/fcxweb/efr/index.html`（FDIC「Securities Exchange Act Filings System」，`fdic.gov/accounting/bank-securities` 頁面裡列出）回應 200 OK，**但是個 JavaScript 驅動的單頁應用（載入 `index.jsp` + jQuery/Bootstrap），本輪只確認連得到，沒有逆向工程它的搜尋 API**——這是留給下一輪的獨立工作單位，如果要判斷值不值得繼續投入。

**這輪沒做的**：沒有逆向工程 `efr.fdic.gov` 的搜尋 API（下一輪如果要接，這是明確定義好的下一步）；沒有查證 SBNY 是否真的是非聯準會會員銀行（假設，未驗證）；沒有查證 FRC 本身是否真的沒有獨立控股公司（假設，未驗證，但跟其 10-K 完全不在 SEC EDGAR 這個直接觀察一致）。這不是因子/策略統計檢定，`TRIALS_LEDGER.md` 不需要加列。完整探測過程見 `sec_edgar_frc_root_cause_probe.py`（純打 SEC EDGAR + FDIC.gov 公開頁面，不碰 FinMind／alpha.db，holdout 規則不適用）。

### 美股 PIT 資料源調查（續）：XBRL company facts API 實測，發現「比較期重複揭露」陷阱（2026-08-24 馬拉松第十輪實測）

**性質：已實測驗證，且發現一個第三輪 submissions API 調查沒有踩到的重要方法論陷阱。** 用 `research/sec_edgar_xbrl_facts_probe.py` 對第三輪已驗證的三個 CIK（AAPL/MSFT/PLTR）打了 `data.sec.gov/api/xbrl/companyfacts/CIK{cik}.json`，全部 200 OK。

**表面上看起來能用**：每個 XBRL concept（例如 `EarningsPerShareDiluted`）底下每筆資料點確實同時有 `end`（財報期間結束日）跟 `filed`（申報日）欄位，文件轉述屬實。AAPL 的 `EarningsPerShareDiluted` 有 338 筆資料點，回溯到 `end=2007-09-29`。

**但天真地用 `filed - end` 算 PIT gap 會算錯**：AAPL 這個 concept 算出來的 gap 是 min=25／max=772／avg=282.3 天——772 天完全不合理（超過兩年）。追查發現原因：**company facts API 是「每個資料點」層級，不是「每次申報」層級**。同一個財報期間（`end` 日期）的數字，會在後續申報裡以「比較期（comparative period）」的形式被重複揭露——例如 2023 年的 Q1 數字，不只出現在 2023 年申報的那份 10-Q 裡，隔年 2024 年的 10-Q 為了年比年對照，也會把去年同期數字再報一次，company facts API 把這兩次都算成獨立資料點。實測驗證：AAPL 74 個不同 `end` 日期裡，**71 個（96%）被超過一次申報引用**，抽樣三筆都是這個模式（例如 `end=2008-09-27` 被 2009-10-27 的 10-K 跟 2010-10-27 的另一份 10-K 各報一次）。

**這代表**：如果要用 company facts API 做 PIT 對齊，不能直接拿 `filed` 欄位當「這個數字第一次公開的日期」，必須先對每個 `end` 分組、取**最小**的 `filed`（第一次揭露），才是正確的 PIT 時間點；否則會把「比較期重複揭露」的較晚 `filed` 日期誤當成原始揭露日，導致 PIT gap 被嚴重高估（本次實測 max 772/1034 天的離群值就是這樣來的）。**這個陷阱是 submissions API（第三輪）沒有的**——submissions API 是「每次申報」一筆記錄，`filingDate`/`reportDate` 本來就是申報層級的一對一關係，沒有比較期重複的問題；company facts API 換了一個更細的粒度（每個數值點），代價是引入了這個新陷阱。

**另一個發現（XBRL taxonomy concept 名稱不穩定）**：`Revenues` 這個 concept 在 AAPL 只有 11 筆資料點、最早 `end=2016-09-24`；但 `EarningsPerShareDiluted` 同一家公司卻回溯到 2007 年。推測原因是 AAPL 早期用不同的 concept 名稱（例如 `SalesRevenueNet`）申報營收，2016 年前後才改用 `Revenues` 這個標籤——**如果要用 company facts API 抓長期營收歷史，不能只查單一 concept 名稱，需要先調查同一語意在不同年代對應哪些 concept 名稱，這輪沒有進一步查證，留給下一輪或之後真正要寫美股版 `factors.py` 時處理。** PLTR 的 `Revenues` concept 甚至完全不存在（`NOT PRESENT`），另一個提醒：不同公司/不同時期用的 concept 名稱不能假設一致。

**還沒驗證的部分**：只測了 3 檔股票、2 個 concept（EPS、Revenues），沒有系統化列出「哪些 concept 名稱在哪些年代適用」；`filed` 欄位取最小值分組後的 gap 分布沒有重新算過（這輪只確認了陷阱存在，沒有算出「修正後」的正確 gap 統計，因為那需要先決定分組/取最小值的實作方式，屬於下一步工作）。

**結論**：XBRL company facts API 可用，但**不能直接照抄 submissions API 的簡單邏輯**——如果之後要選它當美股版 `pit.py` 的資料源，必須實作「同一 `end` 取最小 `filed`」的去重邏輯，且要處理 concept 名稱隨時間變化的問題。這不是因子/策略統計檢定，`TRIALS_LEDGER.md` 不需要加列，跟第二～九輪地基工作的先例一致。

### 美股 PIT 資料源調查（再續）：修正後（同一 `end` 取最小 `filed`）的 gap 統計，以及殘留離群值的成因（2026-08-24 馬拉松第十一輪實測）

**去重後大幅改善，中位數變得合理**：
| 股票／concept | RAW（第十輪，未去重）min/max/avg | DEDUPED min/max/avg/median |
|---|---|---|
| AAPL EPS（74個distinct end，313→74筆） | 25/772/282.3 | 25/**759**/60.6/**32** |

| MSFT EPS（76個distinct end，311→76筆） | 18/1034/287.3 | 18/**1034**/93.9/**28** |

| PLTR EPS（29個distinct end，78→29筆） | 34/788/266.0 | 34/**788**/118.3/**40** |

**中位數（32/28/40天）已經接近submissions API第三輪測到的水準（AAPL平均33.1天/MSFT平均27.5天），代表去重邏輯本身是對的，多數資料點的離群值確實是「比較期重複揭露」造成，不是真的PIT gap。** 但 `max` 幾乎沒變（AAPL 759天、MSFT 1034天、Revenues更慘，去重後平均反而還變高，因為Revenues樣本數太少、離群值占比高，平均被拖走）——**代表去重沒有完全解決問題，還有殘留的真實離群值，不是去重邏輯本身的bug。**

**追查殘留離群值的成因，發現兩個獨立、但同樣重要的陷阱：**

1. **AAPL／MSFT 的離群值全部集中在 `end` 落在 2007–2009 年之間**（實際輸出：AAPL 5筆離群值end日期橫跨2007-09-29～2009-03-28；MSFT 8筆離群值橫跨2007-09-30～2009-06-30，外加一筆2011-12-31較小的208天離群值）。抽樣核對 MSFT 最大離群值（`end=2007-09-30`, `filed=2010-07-30`, gap=1034天）的原始資料列：這筆資料的 `fy=2010`、`form=10-K`——**是MSFT 2010年那份10-K的「五年精選財務數據」比較表格重新揭露2007年Q3的數字，不是2007年當時原始申報的內容**。真正原始揭露（MSFT 2007年當時申報的10-Q）幾乎確定是存在的，只是那份申報**沒有被XBRL標記**（SEC強制大型申報者用XBRL標記財報是2009年中左右才開始分階段生效），所以company facts API裡完全沒有那份原始申報的紀錄，min(filed)撿到的只能是「這個數字第一次被XBRL標記」的日期，不是「這個數字第一次公開」的日期。**這代表：對於`end`早於公司XBRL強制標記生效日（大型申報者約2009年中）的財報期間，company facts API的`filed`欄位系統性地嚴重高估真實PIT gap，不是隨機雜訊，是結構性偏誤，且無法用去重邏輯修正——因為真正的原始申報資料根本不在這個API的資料源裡。**

2. **PLTR 的離群值成因不同，是「上市前期間」，不是「XBRL標記時間」的問題**（實際輸出：5筆離群值end日期是2018-12-31／2019-09-30／2019-12-31／2020-03-31／2020-06-30，PLTR 2020年9月底才上市）。私人公司上市前不對外公開申報SEC定期報告，所以這些上市前期間的數字**第一次公開揭露必然是在上市後**（PLTR的S-1/上市後首份10-K/10-Q把上市前歷史數字當比較期資料揭露），**這不是資料陷阱，是真實的結構性事實**——上市前沒有「更早的原始揭露」可言，min(filed)撿到的日期在這個情境下反而是正確的最早公開日。

**這代表未來設計美股版 `pit.py` 時，同一個「離群值」現象背後有兩種截然不同的處理方式**：
- 第一類（pre-XBRL-mandate，AAPL/MSFT型）：這是資料源的結構性缺口，應該把`end`早於公司XBRL強制生效門檻（概念上約2009年中，但確切日期依申報人規模分級而不同，這輪沒有查證每家公司的確切生效日）的資料點**標記為「PIT gap 不可信，資料源本身缺口」**，不能拿去用，也不該勉強假設「反正取最小filed就是對的」。
- 第二類（pre-IPO，PLTR型）：這是真實的公司生命週期事實，`end`早於公司IPO日的資料點，PIT gap本來就會很大，**這是正確的、不需要修正的訊號**，回測時只要確保這類公司在上市前根本不會被納入宇宙即可（`universe.py`的存活者偏差機制如果延伸到美股，理論上要能自然处理這點，但這輪沒有驗證是否真的如此）。

**還沒驗證的部分**：只測了3檔股票、2個concept；沒有查證AAPL/MSFT等公司各自確切的XBRL強制標記生效日期（只用「~2009年中」這個概略時間點做形狀比對）；沒有測試「排除pre-XBRL-mandate期間、排除pre-IPO期間」後的gap統計是否會全部落在合理範圍（這是驗證上述兩個假說的直接方法，留給下一輪）；沒有測試更多公司樣本以確認這兩種模式是否普遍成立，還是只是這3檔剛好如此。

**結論**：dedup（同一`end`取最小`filed`）是必要但不充分的修正——中位數已大幅改善且貼近submissions API水準，但殘留離群值不是隨機雜訊，而是兩個可辨識、可分類的結構性成因（pre-XBRL標記缺口、pre-IPO歷史資料）。這不是因子/策略統計檢定，`TRIALS_LEDGER.md` 不需要加列，跟第二～十輪地基工作的先例一致。

### 美股 PIT 資料源調查（三續）：`era_reliability()` 的個股層級盲點是否可修——filer category 欄位探測（2026-08-25 馬拉松第70輪實測）

**背景**：第65輪的 `era_reliability()`（`us_pit.py`）用單一 SEC 全市場加速申報人時間表判斷每次申報的 PIT 可信度，但不知道個股自己的申報人分級歷史，對近期 IPO 股（PLTR 實測 14/24 誤判率）不可信。`US_MARATHON_STATE.md` 下一輪建議工作單位第12項問：SEC 公開 API 是否有個股逐年的申報人分級資料可以補這個洞？這輪用 `research/sec_edgar_filer_category_probe.py` 對同樣三個已驗證 CIK（AAPL/MSFT/PLTR）測了兩個候選欄位。

**結果 1：`submissions/CIK{cik}.json` 頂層 `category` 欄位——存在，但只是「今天」的單一快照**：AAPL/MSFT/PLTR 三檔今天都顯示 `"Large accelerated filer"`。**這個欄位沒有日期/申報context，跟 `filings.recent` 不同**——對 PLTR 這種早年不太可能是「Large accelerated filer」的情況完全沒有資訊量，等於沒解決問題。**這是跟 `USStockInfo`／`company_tickers.json` 同一類地雷（快照 vs. 歷史）在美股財報端的又一個實例，不是新陷阱，是同一個陷阱的第三次出現。**

**結果 2：XBRL company facts 的 `facts.dei.EntityPublicFloat`——確實有逐年資料，是比 `category` 更有潛力的路徑**：三檔都測到多筆逐年資料點，每筆帶 `end`（衡量日）／`filed`（申報日）／`fy`（會計年度）／`val`（美元）。AAPL 19 筆（2009–2025）、MSFT 17 筆（2009–2025）、PLTR 6 筆（2020–2025，從 IPO 當年開始，第一筆 `end=2020-09-30` 就是上市當天，公眾流通市值 $133 億）。**這個欄位不是「申報人分級標籤」本身，而是 SEC 規則據以判定分級的原始輸入（公眾流通市值門檻制）**——理論上可以搭配一份「歷史門檻時間表」（跟 `era_reliability()` 的 `_ERA_SEGMENTS` 同精神）自己反推每年的分級，但**這輪只確認資料存在，沒有做反推邏輯，也沒有查證歷史門檻本身**（門檻本身隨時間變過，這輪完全沒查證，不能假設現在的門檻適用全部歷史年份——這正是 `_ERA_SEGMENTS` 當初要解決的同一類問題，如果要接這條路，門檻時間表需要一樣嚴謹的 WebSearch 查證，不能用猜的）。

**留給下一輪（如果要接這條路，三個子步驟，建議分輪做，不要一輪塞完）**：(a) WebSearch 查證 SEC accelerated filer／large accelerated filer 公眾流通市值門檻的歷史變動時間表（例如 2018年、2020年都有規則修正，這輪完全沒查，只是聽過有變動這件事，沒有查證細節）；(b) 寫反推邏輯（給定某年 `EntityPublicFloat` + 對應年份的門檻表 → 推論當年分級）；(c) 拿 PLTR 已知的14/24誤判樣本重新測，看反推出來的分級能不能改善 `era_reliability()` 的準確率。**如果查證後發現門檻歷史太複雜/不確定性太高，也可以決定放棄這條路，改採第41輪『退而求其次』選項——把 `era_reliability` 用途限縮成「只信任已驗證過的長年掛牌大型股，其他一律標記`unverified`」，這仍然是合法的結論，不是失敗。**

**結論**：這輪把「第12項」從「完全開放的問題」推進到「有一條具體、有資料支撐的候選路徑，但門檻歷史表還沒查證，反推邏輯還沒寫」——是一輪探測性的地基工作，不是完整解法。這不是因子/策略統計檢定，`TRIALS_LEDGER.md` 不需要加列，跟第二～十一輪 PIT 地基工作的先例一致。

## 3. 財報 Point-in-Time（公布時點 vs. 所屬期間）

這是**最容易被忽略、也最危險**的一項——如果沒發現，回測會用「還沒公布的財報」去下單，數字會好看到不真實。

### `TaiwanStockFinancialStatements`（季報）
```
curl ".../data?dataset=TaiwanStockFinancialStatements&data_id=2330&start_date=2025-01-01"
```
回傳欄位只有：`stock_id / value / date / type / origin_name`。**`date` 是財報所屬季度的期末日（如 "2025-03-31"），完全沒有公告日期欄位。**

台灣上市公司公布 Q1 財報的**實際時間通常是 5 月中，Q2 是 8 月中，Q3 是 11 月中，年報+Q4 是隔年 3 月中**（依主管機關規定），跟期末日之間有 45 天以上的落差。**如果直接拿 `date`（期末日）當作「這天已經知道這些數字」去跑回測，等於是提早 1.5 個月看到財報，是嚴重的未來函數。**

**✅ 已處理（2026-08-22，決策）：** 還沒找到真實公告日資料源前，一律採「保守發布延遲」假設：`research/pit.py` 的 `quarterly_pit()` 把每季的 `pit_date` 設為 **期末日 + 45 天**（例如 2025-03-31 季末 → `pit_date=2025-05-15`），並在每一列標記 `pit_source='assumed'`（跟真實公告日區分開，不會偽裝成「這是真的」）。

**規則說明：** 這是使用者明確指定的保守假設，不是精算過的最佳延遲天數——目的是「寧可晚一點才讓策略看到財報，也不要提早看到」，避免未來函數。真實公告日通常因公司而異（有些公司常態性提早或延後公告），45 天只是一個統一的安全下界，之後若真的接到公開資訊觀測站的公告日資料，要整批替換掉這個假設。

**任何用到 `pit_source='assumed'` 資料的回測結果，一律視為實驗性、不可採信為乾淨的驗證結果**（`research/pit.py` 有 `any_assumed(df)` 可以檢查一份 DataFrame 有沒有沾到假設值，回測報告要據此標註）。純價格策略（Weinstein 第二階段、動能）完全不會呼叫這個模組，不受此限制。

### `TaiwanStockMonthRevenue`（月營收）
```
curl ".../data?dataset=TaiwanStockMonthRevenue&data_id=2330&start_date=2025-06-01"
```
比財報好一點：有 `create_time` 欄位。**但只有近期資料（約從 2026-04 起）的 `create_time` 有實際日期，更早的月份 `create_time` 是空字串 `""`。** 月營收的 `date` 欄位本身也不是公告日，而是「隔月 1 號」這種記錄日期（例如 2025-06-01 對應的是 5 月營收，實際上市櫃公司月營收要到隔月 10 號左右才公布——`create_time` 為 2026-04-21 對應 2026 年 3 月營收，跟法規的「次月 10 日前公布」大致吻合，可信）。

**結論：**
- **近期（約 2026-04 之後）的月營收有可信的真實公告時間戳，可以拿來做嚴謹 PIT 回測。**
- **更早期的月營收沒有公告時間戳，只能用「次月 10 號」這種規則近似**（跟財報一樣是權宜之計）。
- 這比財報季報好處理，因為月營收公告日期規則相對單純固定（次月 10 日前），財報公告日期則因公司而異、沒有這麼統一的近似規則。

**✅ 已處理（2026-08-22）：** `research/pit.py` 的 `month_revenue_pit()` 實作了這個優先序：`create_time` 有值就用真的（標 `pit_source='real'`），沒有就退回「營收所屬月份的次月 10 日」規則（標 `pit_source='assumed'`）。用 2330 實測：2026-03 營收之後的列全部是 `real`（`create_time` 直接對應 FinMind 記錄的公告時間，例如 2026-04 營收 `create_time=2026-05-08`，跟法規「次月 10 日前」一致但更精確）；再往前的列全部正確退回 `assumed` 並標上規則算出的日期。

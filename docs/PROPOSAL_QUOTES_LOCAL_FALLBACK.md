# 提案：盤中報價本機備援（GitHub 高頻排程不可靠）

先.八十一-25｜2026-10-13｜狀態：**等總司令裁示，未動工**

## 1. 問題（有證據）

- `quotes.yml` 排了台股交易時段每 10 分鐘一班（UTC 01:07～05:37，台北 09:07～13:37，約 28 班／日）。
- `gh run list --workflow quotes.yml` 實際紀錄：
  - 10/12 整天只跑 4 班，台北 07:16、12:59、17:39、23:45。
  - **10/13 上午盤中 0 班**，`data/quotes_tw.json` 停在 07:46 開盤前那份。
- 開盤前那份每列都是「昨收頂上、`stale:true`」。App 原本沒看這個旗標，首頁自選股整排顯示「+0.00%」。這一點已在先.八十一-24 修好：stale 列不當報價、盤中舊收盤標日期。
- **App 不再顯示錯誤數字，但盤中仍然沒有近即時報價**。目前盤中唯一的近即時來源是本機永豐（Shioaji）；手機沒連上電腦就看不到。`quotes_sinopac.json` 自 10/12 收盤後未連線。
- GitHub 官方文件說明排程在高負載時可能延遲或被丟棄；高頻 cron 本來就不保證準時。

## 2. 提案做法

本機新增排程 **AlphaQuotesFallback**，只在台股交易日 09:05～13:40、每 10 分鐘一次：

1. 先看雲端那份 `data/quotes_tw.json` 的最後提交時間（`git log -1 --format=%ct`，比照新聞備援 `news_local_fallback.py` 的做法）。
2. **雲端 12 分鐘內有更新就什麼都不做**，避免與雲端重複。
3. 雲端落後才在本機跑 `.github/scripts/fetch_quotes_tw.py`（同一支程式、同一套 MIS 節流與封鎖紀錄），產出 `data/quotes_tw.json`。
4. 用 `scripts/local_git_commit.commit_paths(..., drop_on_conflict=True)` 只提交這一個檔，流程是：取鎖（帶 token）→ commit → pull --rebase → push；和雲端衝突就作廢本機這輪。
5. 休市日（`data/trading_calendar.json`）與非交易時段直接結束。

## 3. 量的估算

| 項目 | 估算 |
|---|---|
| MIS 請求 | 每班約 5～10 次（238 檔，每批 50 檔，上市只查 tse_ 前綴、不確定者兩前綴都查），同源間隔 ≥3 秒。**最壞**每日 28 班全由本機跑，約 140～280 次。雲端有跑的班次本機不跑，實際更少 |
| 對 MIS 的頻率 | 與雲端原設計相同（每 10 分鐘一輪），不增加尖峰頻率；只是把「雲端沒跑的班」補上 |
| commit 數 | 最壞每日約 28 個（每個只含 `data/quotes_tw.json` 約 53KB）。git 壓縮後每個約 10KB 以下 |
| 本機資源 | 每班約 30 秒；電腦要開著才有效 |

## 4. 風險

1. **電腦關機或離線時沒有效果**：和現在的永豐即時源同一個限制，但至少電腦開著時不必依賴手機連線。
2. **commit 量增加**：最壞每日多 28 個小 commit。可改成「只在雲端落後超過 20 分鐘才補」，降到每日約 10 個。
3. **與雲端同時寫同一檔**：`drop_on_conflict=True`，衝突就作廢本機這輪，以雲端為準。git_op_lock 已改成帶 token（先.八十一-34），不會誤刪別人的鎖。
4. **MIS 封鎖風險**：共用 `data/rate_limit_state.json` 的節流與 2 小時封鎖紀錄。被封就整段停止，不重試。
5. **本機 git pull 換大檔的競態**：每次 pull 都可能換 price_history.json，造成讀取端短暫讀不到。先.八十一-31 已在讀取端加重試。本備援只提交 quotes_tw，不會增加 price_history 的換檔次數。

# 提案：要不要從 git 歷史移除 price_history.json 大檔

建立：2026-10-13（總司令【先.八十二】1）。**只是提案，不執行。** 改寫 git 歷史屬於不可逆操作，需要總司令裁示才可以做。

## 現況（2026-10-13 實測）

- `data/price_history.json` 已改成拆檔資料夾 `data/price_history/`：11 個分桶，每檔約 3～5MB，另有 `_meta.json`。舊的單一大檔從最新版本移除。
- **舊大檔仍留在 git 歷史裡**：
  - 共 89 個版本，原始大小合計約 4.2GB。
  - 實際占用的壓縮後空間只有約 **33MB**。git 會把相鄰版本存成差異，所以壓縮率很高。
- 整個 repo 壓縮包約 **223MB**，舊大檔只占其中約 15%。
- GitHub 的 100MB 上限是「推送時，單一檔案的單一版本」。舊版本每份都在 76MB 以下，而且早已推送成功。**從現在起不會再有大檔推送**，所以上限問題已經靠拆檔解決，跟歷史無關。

## 選項

| 選項 | 做法 | 好處 | 代價與風險 |
|---|---|---|---|
| **甲、不改歷史（建議）** | 什麼都不做 | 零風險 | repo 會一直多留約 33MB 的舊版本 |
| 乙、改寫歷史移除舊檔 | 用 `git filter-repo --path data/price_history.json --invert-paths` 改寫全部歷史，再強制推送 | 壓縮包約少 33MB（223→約 190MB） | **不可逆**。①所有 commit 編號都會改變，PROGRESS.md、PENDING_QUEUE.md、REPORT.md 裡數百處引用的 commit 編號全部失效，稽核軌跡斷掉。②本機、雲端排程與 Cowork 的每一份 clone 都要重新 clone，否則下一次 push 會把舊歷史推回去。③強制推送期間若有排程同時推送，會丟資料。④GitHub 伺服器端的舊物件不會立刻清掉，要另外請 GitHub 支援清除 |
| 丙、日後真的需要時再做 | 等 repo 大到影響 clone 或 Actions 速度，再評估 | 先不承擔風險 | 無 |

## 建議

採 **甲**。這次的問題是「單檔逼近 100MB」，已經用拆檔解決。改寫歷史只能省下約 33MB（約 15%），卻要賠上所有 commit 編號引用的稽核軌跡，還要讓每一份 clone 都重來，得不償失。若日後 repo 變大到影響速度，再走丙重新評估。

## 不裁示的後果

維持甲：沒有任何功能影響。

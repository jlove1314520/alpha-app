## 二、防護方案（每項都要總司令決定）

### a. 電源計畫（影響：小；建議：大部分已經是對的）

現況（10/15 只讀查證）：電源計畫「平衡」、**插電睡眠＝永不（已是）**、螢幕關閉＝15 分鐘、
這台支援的是「現代待命（網路保持連線）」。今天證明螢幕關閉後的待命**不會**擋住 S4U 工作與網路。

建議（總司令在「設定 → 系統 → 電源」或系統管理員 PowerShell 自己操作）：
- 維持插電睡眠＝永不；另把**插電休眠也設成永不**：`powercfg /change hibernate-timeout-ac 0`
- 網路卡不省電：「裝置管理員 → 網路介面卡 → Killer Wi-Fi 6E → 內容 → 電源管理」取消勾選
  「允許電腦關閉這個裝置以節省電源」。
- **更穩的做法：插網路線**。這台有 Killer 2.5G 有線網卡，目前是「已中斷連線」，現在全靠 Wi-Fi。

### b. Windows Update 使用時段（影響：中；建議：立刻做，但單獨做不夠）

「設定 → Windows Update → 進階選項 → 使用時段」改為手動 **07:00～01:00**（Windows 上限 18 小時）。
效果：Windows 只會在 01:00～07:00 之間自動重開，交易日 08:30～20:00 不會再被打斷。
另外建議同頁開啟「需要重新啟動時通知我」。

**限制要講清楚**：就算改到凌晨 03:00 重開，重開後一樣是登出狀態，**隔天整天照樣停擺**——
除非搭配 c，或總司令每天早上看到通知後手動登入。所以 b 是「把重開移到不傷人的時間」，c 才是「重開後自己活過來」。
近期 26H2 功能更新會重試（10/15 失敗 0x8024202B），建議 b 先做。

### c. 重開機後不登入也能執行（影響：大；需總司令本人操作；不採用自動登入）

| 選項 | 做法 | 好處 | 代價／風險 |
|---|---|---|---|
| **c1（建議）存一次 Windows 密碼** | 把需要整天活著的工作改成「不論使用者登入與否均執行」並勾選存密碼（總司令本人在工作排程器輸入一次） | 重開後不用登入就跑；**能存取認證存放區，git push 應可正常**（今天 S4U 推不上去的問題一起解決） | 密碼由 Windows 以 LSA 機密保存；這是 9/10 當時以「真錢帳戶機器」為由暫不採用的選項，需要重新決定 |
| c2 維持現狀（S4U，不存密碼） | 不動 | 不新增祕密 | 今天已證明：S4U 能跑但**推不上去**，Shioaji／IBKR／DevQueue 等仍是登入才跑 |
| c3 每次重開後人工登入 | 搭配 d 的推播，看到就登入 | 零設定變更 | 依賴人；今天這種「人在外面」就救不了 |

c1 若同意，建議範圍分兩批：
- 第一批（資料命脈）：AlphaLiveServer、AlphaShioajiQuotes、AlphaIbkrQuotes、AlphaData、AlphaMarketCatchup、AlphaQuotesFallback、AlphaNewsFallback，外加已是 S4U 的 AlphaConnectivity、AlphaTwsePublishProbe（改存密碼後才推得上去）。
- 第二批（研究／claude CLI）：先單獨驗證 `claude` 在非互動身分能否啟動，通過才改。
- 我會先準備好「逐一備份原 XML → 改 → 實跑一次看產出 → 失敗就還原」的腳本（沿用 `convert-tasks-to-s4u.ps1` 的安全做法），**輸入密碼那一步一定由總司令本人做**。
- IBKR Gateway 重開後仍要人工輸入帳密（官方限制、本專案不代填），c1 救不了這一項。

### d. 停擺告警推播（影響：中；建議：d1 先做）

現況：雲端 `local_schedule_watchdog.yml` 已經會判斷「本機超過 60 分鐘沒心跳」並讓 job 變紅燈，但
①只寄 email；②GitHub 排程常被跳過，今天第一次紅燈晚了約 4.5 小時。

| 選項 | 做法 | 新增祕密／第三方 | 延遲 |
|---|---|---|---|
| **d1（建議先做）GitHub 手機 App 推播** | 總司令在 GitHub 手機 App「設定 → 通知 → Actions」開啟「失敗的工作流程」推播 | 無 | 取決於排程何時跑（今天約 4.5 小時） |
| d2 Telegram 機器人推播 | 新建一個只發訊息的 bot，token 放 GitHub Secrets，紅燈時發訊息 | 新增 1 個 bot token（第三方：Telegram） | 同上 |
| d3 縮短偵測延遲 | 改由外部定時服務（或 Cowork 排程）每 15 分鐘觸發 `workflow_dispatch`，不靠 GitHub 自己的排程 | 需要一個能觸發 workflow 的 token | 約 15～75 分鐘 |
| d4 本機自報「剛重開、沒人登入」 | S4U 的 AlphaConnectivity 偵測「開機後沒有使用者工作階段 > 10 分鐘」就寫告警 | 無 | **推不出去**（同附帶發現 1），除非先做 c1 |

建議組合：**b＋d1 先做（零風險、總司令 5 分鐘內可完成）→ 總司令決定 c1 → c1 通過後再加 d4。**
